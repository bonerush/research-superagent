# 研究代理设计（Research Superagent）

分支：`doc/research-superagent-design`

> 本文用中文写。核心术语（判死、点头、议程、验收契约）是对话中定下的，翻成英文会丢。定稿后另出英文版并入 `docs/00x`。

## 摘要

一个人类（领导）加一群 agent（研究组），把一条研究方向从模糊想法推进到「可复现证据 + 结论报告」。人只在三处点头：**签契约、判死、收成果**。其余全部自动。

现有仓库是一个多用户、事件驱动的 coding agent：Source 产生 Trigger，Eval 判「谁有权提这个活」，Ticket 带授权派给 Executor。研究循环的前提正好相反——请求方是 agent，唯一审批者是一个人类，工作单元要活几周而不是一个工单。所以换的是域模型，留的是基建。

## 1. 为什么做

- 研究的瓶颈不是写代码，是**判断**：新不新、值不值得做、证据够不够、该不该停。
- 这三类判断现在都要人做，而且时机很糟：等实验跑完才看到方向错了。
- 所以把钱和算力花在**前置**：让它在纸上（提案、协议、判据）多花功夫，在机器上少花。

## 2. 目标 / 非目标 / 反目标

| | |
|---|---|
| **目标** | 一条方向从提案到报告全自动，中间不需要人盯 |
| | 每个结论可追溯到 run、机器、commit、参数 |
| | 每个尝试的机时与金额可归集到方向 |
| | 失败与走死的路径被记录并被议程吸收，不重复烧钱 |
| **非目标** | 多用户权限体系（没有外部陌生人） |
| | 自动投稿、自动联系合作者 |
| | 湿实验 |
| | 通用 coding agent |
| **反目标**（技术成功但这件事失败） | 报告很多，但人一份都不看 |
| | 把噪声当结论，或把失败包装成「还需要更多算力」 |
| | 烧光余额，而人不知道为什么 |
| | 分支树烂到没人能读出实验历史 |

## 3. 约束

AutoDL 一类租用 GPU（已核对官网计费与 API 文档）：

| 事实 | 后果 |
|---|---|
| 按开关机时间计费，关机即停，精确到秒 | 空闲一分钟都是钱 |
| 关机后数据保留一段时间 | 环境靠磁盘活着，不必常开 |
| 关机后 GPU 不预留，下次可能被租走 | 协议要声明占机时长，或接受等待 |
| 无卡模式 ¥0.1/小时（0.5 核 / 2G / 无卡） | 改代码、传数据、写结论走这一档 |
| 关机后标准输出不可见 | 日志必须自己落盘 |
| 有开放 API，能 create / power_on / power_off | 开机可以程序化，但需要账号开通并持有 token |
| 官网余额即预算上限 | 不建预算系统，只建账本 |
| **只租一台机器** | 实验天然串行，机器时间是唯一瓶颈；排期是队列，不是并发 |

其他约束：git 分支模型沿用 `dsh-obsidian-mem`；单账户、单仓库；可用模型包括同模型不同提示与不同模型。

## 4. 域模型

### 4.1 概念

| 概念 | 是什么 | 不变式 |
|---|---|---|
| **Lab** 实验室 | 仓库 + 机器池 + 环境镜像 + 数据 | 主工作区只放跨尝试复用的东西；一次尝试的产物只在该尝试的分支上 |
| **Agenda** 议程 | 长生命周期的研究方向集合，不属于任何一次尝试 | 唯一长期记忆；结论只能从这里被读到 |
| **Question** 问题 | 方向 / 选题 / 假设是同一对象的不同精度 | 到 `hypothesis` 精度时必须带 `prediction` 与 `test` |
| **Proposal** 提案 | 一批候选方向（默认 5 份） | 没有最近先例（≥3 篇）与 delta 的提案不交付 |
| **Contract** 验收契约 | 人签一次后冻结的验收基准 | 冻结后改动等于新契约 |
| **Protocol** 实验协议 | 某次尝试的事前登记 | 必须与所引契约的判据一致；不一致由批判 agent 打回 |
| **Attempt** 尝试 | 一条分支 + 一份协议 + 一组 run + 一个 verdict | 提案人与判定人不能是同一个人格的上下文 |
| **Run** 运行 | 一次上机：机器、镜像、commit、命令、参数、起止、金额、日志、产物 | 没有 run 的结论是意见 |
| **Member** 成员 | agent 的身份、角色、归属 | 每个动作都记 member id |
| **Decision** 决定 | 人做的一个判断：签契约 / 判死 / 收成果 | 只有人能产生；agent 只能建议 |

**契约与协议的分工（评审第 4 条）。** 契约定的是「做成什么样」：目标、要求（如「架构创新」）、验收判据、预算上限、停止条件、容差。协议定的是「这次怎么做」：命令、数据、镜像、判据的落实方式、占机时长、预期值。**人签的是判据，不是命令**；协议按契约派生，由批判 agent 校验一致性，不需要人再签。这样「人只签一次」才成立，attempt 也不必每次重签。

### 4.2 基数

| 关系 | 基数 | 说明 |
|---|---|---|
| Proposal → Question | 1 : N | 每份候选就是一个 Question 草稿；选中的那一份冻结 statement，其余记为 rejected（带拒绝理由，是品味信号） |
| Question → Attempt | 1 : N | 一个假设可以被反复试；每个 attempt 各自带协议 |
| Attempt → Run | 1 : N | 含验证性重跑 |
| Attempt → Contract | N : 1 | 引用某个**不可变**的契约版本 |

### 4.3 状态机

```
Question:  open ─→ testing ─→ answered | abandoned
Attempt:   opened ─→ running ─⇄─ waiting ─→ concluded(supported|refuted|inconclusive)
                                        └→ abandoned
Run:       queued ─→ started ─→ finished | failed | killed
Machine:   off ─→ booting ─→ idle ─→ running ─→ idle ─→ off
                └─(无卡)─→ idle_nocard ─→ off
```

verdict 与 Question 状态的映射（评审第 6 条）：

| Attempt verdict | Question 状态 | 谁写 |
|---|---|---|
| supported | answered（正面） | 实验角色提议，记账角色写入 |
| refuted | answered（负面，作为结论保留） | 同上 |
| inconclusive | 保持 testing，或由人判 abandoned | 人 |
| abandoned | 保持 testing，直到人判 | 人 |

### 4.4 不变式（八条，都要能写进代码）

1. 契约冻结后不可修改；要改就开新契约版本，旧尝试仍按旧版本判。
2. 任何结论必须指向至少一个 run；没有 run 的结论只能是 proposal。
3. 删分支之前，该尝试的结论必须已经写进议程（以 `agendaEntryId` 引用）。
4. 关机之前，日志必须已经落盘。
5. 判死只能是一条人的 Decision；agent 只能提交建议和证据。
6. 提案人与批判人不能是同一个上下文。
7. 机器空闲满 1 小时（无 job、无会话、无传输）自动关机，不需要人批。
8. 单个尝试的累计开销达到契约上限时，进入 `waiting` 并通知人。

## 5. 循环

### 5.1 入口与驱动器（评审第 3 条）

**入口只有三个**：

1. 人在面板上写一段方向（自由文本 + 可选约束）。
2. 人在主会话里直接说。
3. 议程里已有 `open` 的问题，到了该再试的时候。

**驱动器**是宿主进程里的一个 tick（沿用现有 `passes` 的机制，每 2 秒一次）。每个 tick 只做三件事：跑到期任务、守护机器、排期。它不思考、不做判断，判断都在角色会话里。

**排期是队列。** 只有一台机器，所以一次只跑一个尝试，其余排队；队列顺序由议程按「信息增益 ÷ 预计机时」排，人可插队。机器在跑的时候，探路、批判、写作照样能开工——纸上作业不占机器，这是唯一存在的并行。

**「值不值」的判定者是人**：批判 agent 只负责杀「明确不新、明确做不了」的，剩下的端给人挑。文档此前把这一层含糊过去了，这里写死。

### 5.2 阶段一：提案（便宜，都在纸上）

```
画像 + 文献扫描
      ↓
5 份候选提案（问题 / 为什么现在 / 先例与 delta / 可行性 / 协议草稿 / 最可能失败处）
      ↓
批判 agent 预筛（保守：只杀明确不新、明确做不了的）
      ↓
人选一个 → 契约定稿 → 人签 → 冻结
```

一次给 5 个的理由：人说不清自己想要什么，但认得出。挑选本身就是免费的偏好标注。

### 5.3 阶段二：执行（贵，都在机器上）

```
议程排期 → 开 attempt 分支 → 写协议（事前登记：命令、数据、判据落实、预期、占机时长）
      ↓
开机（或先无卡模式备环境）→ 跑 → 日志落盘 → 关机
      ↓
证据归档：run 记录 + 日志 + 产物 + 金额
```

协议必须**事前登记**。没有它，「程序走完了没有」无法核查，它会永远说「还差一组消融」。

### 5.4 阶段三：收敛

```
读证据 → verdict → 结论写回议程（含走死的路）
      ↓
要交结果时：clean checkout 重跑 → 证据包 + 报告 → 人验收 → 判死或继续
```

## 6. 机器

### 6.1 控制面与执行面（评审第 1 条）

- **控制面**：AutoDL 开放 API（`create` / `power_on` / `power_off` / `status` / 余额），需要账号开通并持有 token。凭据只存在宿主机、不写进会话提示词。
- **执行面**：SSH。只在机器已经 running 后使用。
- **监督进程**：跑在**宿主机**，作为插件的一个 effect/定时任务，不在远端。原因：它是唯一能在机器关机时还活着的位置。
- **远端可观测性**（怎么判「没有 job / 会话 / 传输」）：
  - 没有 job：约定每个 run 在 `/lab/runs/<run-id>/` 下留 `pid` 与 `done` 标记；无 `pid` 或无进程、也无 `done`，视为空转。
  - 没有会话：`who` 与 `ss -tn` 的连接数为 0。
  - 没有传输：无 `rsync`/`scp`/`rclone` 进程，且最近 N 分钟无新文件。
- **失败语义**：开机失败重试 3 次（间隔递增）；被抢占则换卡型或排队等待，超过 T 分钟通知人；关机调用失败则告警并保持监督。

账号已确认可开通开放 API，因此开机全自动，不设第四个人工点。若 token 失效或余额不足，退化路径是「人在面板点开机」并告警。

### 6.2 三档状态

| 状态 | 花费 | 干什么 |
|---|---|---|
| 关机 | 只有存储 | 默认态 |
| 无卡模式 | ¥0.1/h | 改代码、传数据、整理结果、写结论 |
| GPU 开机 | 按卡计费 | 只为跑实验 |

### 6.3 双重关机

1. 第一层，脚本自带：实验命令后挂 `/usr/bin/shutdown`，跑完自动关。
2. 第二层，宿主机监督：无 job、无会话、无传输满 1 小时则关机。

第一层会在进程崩溃、服务卡住时失效，第二层接住。

### 6.4 账本（评审第 5 条）

- **金额**：`run.cost = Σ(每段时长 × 该段卡型单价)`。单价来自配置（按卡型），不靠猜。
- **共享归因**：机器成本归**发起开机的那次尝试**，包括它自己的空闲段。无卡模式备环境产生的成本归「下一个要用它的尝试」。
- **余额**：控制面 API 查；低于硬下限（建议 ¥50）时拒绝开机并通知人。
- **不变式 8 的落地**：每次 run 结束后累加，达到上限就把 attempt 置为 `waiting` 并通知——这就是状态机里 `waiting` 存在的原因。

## 7. 组

### 7.1 角色到运行实体（评审第 7 条）

| 角色 | 运行实体 | preset | 可读 | 可写 |
|---|---|---|---|---|
| 探路 | 主会话的 subagent | standard | 画像、议程、文献 | `research/proposals/` |
| 实验 | 每个 attempt 一个 worker 会话 | worker | 契约、协议、自己的分支 | 自己的分支、`/lab/runs/` |
| 批判 | 独立 subagent（每次新上下文） | standard | **只有提案的结论与证据** | 无（只返回意见） |
| 写作 | 独立 subagent | standard | 结论、run 记录、报告模板 | `research/reports/` |
| 记账 | 主会话本体 | router | 全部慢状态 | 议程、attempts、分支清理 |

### 7.2 批判层必须是真的

优先用不同模型；同一模型时退到**信息隔离**：批判 agent 在独立目录、独立上下文里工作，读不到提案人的草稿、会话和分支历史，只拿到结构化的提案摘要与证据链接。

只靠提示词说「请严格评审」是没用的——同上下文里它只会复述提案再加一句「有价值」。

## 8. 三个点头点

### 8.1 在哪点、谁能点（评审第 2 条）

- **两个界面，一组动作。** 面板是完整视图；飞书卡片是提醒加快捷动作（带深链）。两者都走同一组**人专用决策路由**（`POST /decisions`），按发送者身份校验——面板会话或飞书 open_id 必须在允许的人里。
- 三个动作**不出现在任何 agent 会话的工具集里**。agent 能读 Decision，不能写。
- 「改一版」= 结构化字段编辑 + 自由文本备注；「打回」= 一条 Decision，带理由。
- 飞书只做「提醒 + 一次点击」，不做长文编辑；要改契约正文回面板。

### 8.2 每一处要交什么

| 点头 | 它交什么 | 人要回答 |
|---|---|---|
| **签契约** | 5 份候选对比、推荐哪份及理由、冻结后的契约（目标 / 要求 / 判据 / 预算上限 / 停止条件 / 容差） | 签，或改一版 |
| **判死** | 程序完成度（跑了哪些、跳了哪些）、结果对照判据、**反方意见**（批判 agent 的反对理由） | 停，或继续 |
| **收成果** | 证据包、报告、它自己 clean checkout 的重跑结果 | 收，或打回 |

判死必须带反方意见：只交「我认为该停」等于没给判断材料。

## 9. 存储与账本

规则：**慢状态进 git，快状态进 store。**

| 慢（人会读、要版本） | 快（会变、只在操作时读） |
|---|---|
| `research/agenda.md` | run 记录、机器状态 |
| `research/contracts/<slug>.md` | 会话、任务、花费流水 |
| `research/attempts/<slug>.md` | 队列、锁、心跳 |
| `research/reports/<slug>.md` | |

### 9.1 议程的写协议（评审第 8 条）

议程条目 schema：

```
id: Q-0007
question: <一句话，精度标签>
status: open | testing | answered | abandoned
conclusion: <一段话，可为空>
evidence: [run ids]
decidedBy: <member id 或 human>
at: <ISO 时间>
```

- **唯一写入者是记账角色**。探路、实验、写作只能提交变更请求。
- 每次收尾是「追加一条 + 一次提交」，不做原地改写，避免并发冲突。
- `attempts/<slug>.md` 与 `reports/<slug>.md` 都是议程条目的**附件**，不是独立事实；冲突时以议程为准。
- 不变式 3 的可检查形式：attempt 文件里必须有 `agendaEntryId`，否则删分支的动作被拒绝。

## 10. 可复现（评审第 9 条）

证据包字段：

```
branch, commit, image, machineType,
dataSnapshot: {kind: hash|path|copy, value},
command, envFile, logs[], artifacts[], metrics{},
reproduce.sh
```

- **重跑在哪儿跑**：允许换卡型。若原卡型不可得，记录实际卡型与耗时差异。
- **复现成功的判据**：同 commit、同数据哈希、同命令，指标在契约给定的容差内。
- **失败分支**：标记 `not_reproducible`，verdict 降级为 `inconclusive`，报告里必须写明，并开一个后续 attempt 或退回实验。
- **这次重跑记在哪个 attempt**：记在原 attempt 下，类型为 `verification`；attempt 已 concluded 仍可追加这类 run。

## 11. 与现有代码的关系（评审第 10 条）

保留的是机制（跟研究无关、跟可靠性有关），换掉的是域。`src` 一万多行（评审实测约 1.5 万）。

| 目录 | 处置 | 备注 |
|---|---|---|
| `core/` | 重写 | 保留 `ids`、`errors`；域逻辑全换 |
| `app/` | 混合 | 保留 `store`、`outbox`、`effects`、`runtime`、`passes` 的骨架；`views/` 重写；`assessment`、`admission` 删 |
| `client/` | 混合 | 面板框架保留；`views/` 与 `eval` 相关重写 |
| `sources/` | 大部分删 | GitHub 全删；飞书缩成通知通道 |
| `executor/` | 保留并扩展 | 会话管理留下，新增机器驱动（API + SSH） |
| `tests/` | 重写 | 跟着新域走 |

**迁移立场**：不迁移旧数据。研究域的语义与工单域没有对应关系，硬迁会造出一堆翻译层。直接换库、换表。

> **2026-11-21 决定（操作者）：旧域保留，不执行删除。** GitHub 仓库用作数据与代码的云存储，git 本身用科研分支管理；删掉 GitHub 监听或工单域会打断这套用法。研究域与工单域并存，删除计划只作存档。

**估算**：不是「中等」。按上表，重写面约 60–70%，删约 15%，留约 15–25%。排期应按这个比例给阶段。

## 12. 备选方案与选择

| 方案 | 做法 | 代价 |
|---|---|---|
| A 在旧域上叠一层 | 议程当作长寿 Thread，提案与契约当作 Input，尝试当作 Ticket | 改动最小，但多用户、事件驱动、一票一目录的假设会一直跟新功能打架 |
| **B 换域留基建（选它）** | 保留机制，重写域；删授权层 | 重写面大，但表与视图本来就要重写 |
| C 回到会话原语重写 | 写编排器，按角色起 DSH 会话，状态放文件 | 最轻，但面板、通知、崩溃恢复全要重造 |

选 B：真正错的是域模型，真正对的是基建。前提是**得先能删**——删不干净，B 会不知不觉退回 A。

## 13. 对话中定下的事

| # | 内容 | 谁定的 |

## 15. 这份设计怎么算通过

1. 一个没参与过这场对话的 builder，能据此排出实施计划。
2. 三个点头点各自的交付物有明确定义，不需要再问。
3. 每条反目标都有一条对应机制，而不是一句愿望。
4. 八条不变式里，没有一条是只能靠提示词实现的。
